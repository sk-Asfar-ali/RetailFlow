# RetailFlow

**An end-to-end lakehouse data platform simulating a real e-commerce business** —
combining batch OLTP ingestion and real-time clickstream processing, transformed
through a medallion architecture (Landing → Bronze → Silver → Gold) on Azure
Databricks with Unity Catalog, ADLS Gen2, and dbt.

Built as a production-grade portfolio project to demonstrate the full
lifecycle of a modern data platform: source systems, ingestion (batch +
streaming), governance, transformation, orchestration, and BI.

> 📄 See [`docs/architecture.md`](docs/architecture.md) for the full system
> design writeup, including key decisions and tradeoffs.

## Architecture at a glance

```
Azure Postgres (OLTP)  ─────┐
                              ├──► Landing ──► Bronze ──► Silver ──► Gold ──► Dashboard
Azure Event Hubs (stream) ──┘      (raw)     (Delta)    (dbt)      (dbt)
```

*(Full lineage graph generated by `dbt docs` — see [screenshot](#dbt-lineage-graph) below.)*

| Layer | Technology |
|---|---|
| Batch source | Azure Database for PostgreSQL (Flexible Server) |
| Streaming source | Azure Event Hubs (Kafka-compatible endpoint) |
| Compute | Azure Databricks (Structured Streaming + JDBC batch) |
| Storage & Governance | ADLS Gen2 + Unity Catalog (Managed Identity, External Locations) |
| Transformation | dbt (dbt-databricks adapter) |
| Orchestration | Databricks Jobs (scheduled, dependency-based DAG) |
| Secrets | Azure Key Vault (linked secret scope) |
| BI | Databricks Dashboards |

## What this project demonstrates

- **Dual ingestion patterns**: incremental watermark-based JDBC batch extraction
  *and* checkpointed Structured Streaming — the two dominant data-integration
  patterns in real platforms, both built and orchestrated end-to-end.
- **Production-style source systems**: a realistic OLTP schema with live
  order/payment/status simulation, and a Kafka-compatible event stream with
  session-aware clickstream generation — not static sample datasets.
- **Proper data governance**: Unity Catalog with Managed Identity auth (no
  hardcoded keys/secrets anywhere), External Locations, and Managed Location
  schemas — all data physically verifiable in an owned ADLS Gen2 container.
- **Tested, documented transformations**: dbt models with source/model tests
  (`unique`, `not_null`, `accepted_values`) and auto-generated lineage docs.
- **Cost-aware architecture decisions**: e.g. choosing scheduled
  `availableNow` streaming over an always-on cluster, sized to actual data
  volume rather than defaulting to the most impressive-sounding option —
  and being able to articulate why.
- **Real debugging & data quality handling**: e.g. discovering and fixing an
  inconsistent-casing issue in clickstream event types at the Silver layer,
  rather than glossing over it.

## Pipeline orchestration

A single scheduled Databricks Job (`retailflow-bronze-ingestion`, every 15
minutes) runs the whole pipeline:

```
setup_catalog
      │
      ├──► bronze_postgres ─────┐
      │                          ├──► dbt_transform (dbt run + dbt test)
      └──► bronze_clickstream ──┘
```

Each run: pulls only new/changed data from both sources, merges into
Bronze, then rebuilds Silver and Gold via dbt — fully hands-off.

## Local development setup

### Source systems
```bash
cd Batch-source-system
docker compose up -d          # local dev only; production uses Azure Postgres
python seed.py --customers 500 --products 200
python simulate_traffic.py --interval 2

cd ../Streaming-system
python produce_clickstream.py --rate 5
```

### dbt
```bash
cd dbt
pip install dbt-databricks
# configure ~/.dbt/profiles.yml -- see dbt/README.md
dbt debug
dbt run
dbt test
dbt docs generate && dbt docs serve
```

Full setup instructions for each component are in their respective
folder READMEs.
